# 同频 V0.6.4 · 批量联网匹配稳定性修复

本版基于 V0.6.3，专门修复 Excel/CSV 批量导入时「第一次搜不到，手动重试却有结果」的问题。双主题、帖子、圈子评分、原有导入勾选规则均保持不变。

## 原因

- V0.6.3 的批量搜索每 750ms 最多启动一个请求，可能达到约 80 次/分，而 Vercel 搜索接口对同一个用户的暖实例限制为 30 次/分。
- 429、网关故障和请求超时都被直接记为“搜索失败”，没有自动退避重试。
- Bangumi 等上游失败可能返回 HTTP 200 与空结果，空列表还可能进入服务端 1 分钟缓存，被误认为确实没有该作品。

## 本次修复

1. **全队列统一限速**：最多 2 个并发，每次启动（包括重试）至少间隔 3400ms，理论约 17.6 次/分钟，为日常找片保留余量。暂时不会因同时开两个 worker 而突破全局限速。
2. **自动重试**：429、408、502/503/504、其他 5xx、网络错误和超时最多尝试 3 次。普通临时故障采用渐进退避；429 优先读取 `Retry-After`，将整个批次进入冷却，避免两个 worker 同时继续冲击限流。
3. **区分无结果和暂时不可用**：新增 `temporaryFailure` 响应标识。实际搜索成功且返回空数据才算无结果；主数据源异常导致的空结果不会再缓存，批量导入自动重试。对新旧服务端混合部署期间的旧错误提示保留兼容。
4. **错误展示**：匹配表中显示“网络拥堵，自动退避重试”，最终失败才展示错误与手动重试。原来的高置信度自动勾选、人工确认、未确认默认不选规则完全保留。
5. **暂停/继续**：等待限流期间可暂停；取消弹窗会终止未完成的等待与请求。恢复后继续处理队列，不会重新覆盖人工取消的勾选。

## 性能取舍

- 为稳定起见，冷启动、没有缓存的 300 条不同作品，单是按 3400ms 间隔发起请求的理论用时就约 **17 分钟**，如发生 429 等退避会更久。
- 搜索依赖浏览器页面保持打开；不属于后台离线任务。Vercel 多函数实例以及不同用户共同用量仍可能触发其他限制。对高需求使用场景可以后续引入持久化服务端队列。
- 这次不添加 Steam 作为来源，游戏仍以 Bangumi 为主，IGDB / RAWG 为配置可选来源。

## 升级

从 V0.6.3：把升级补丁按相同目录结构覆盖 GitHub 仓库后提交，等待 Vercel 自动构建。不需要任何新 SQL 或环境变量。

## 验证

```bash
npm run test:features
npm run test:search
npm run build
```

本地 Node 自动化测试共 87 项通过。服务端网络请求与真实 Supabase 写入仍需在部署后验证，尤其是国内运营商至 Vercel/Bangumi 的网络差异。
